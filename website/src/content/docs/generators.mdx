Writing tests against validators needs valid inputs — but you must never use a real person's PAN or Aadhaar in a test. indycheck's generators produce random values that pass validation, for tests, demos, screenshots and seed data.

There is no generic `generate(type)` dispatcher. Only six generators exist, one per type:

## Usage

```js
import { generatePan, generateAadhaar, generateGstin, generateMobile, generateVehicle, generateVehicleBharat } from 'indycheck';

generatePan();          // e.g. 'HMSTC9464C'  — random every time
generateAadhaar();      // e.g. '262200939149' — passes Verhoeff
generateGstin();        // e.g. '13NFAPJ0888B1ZM' — passes Mod-36 Luhn
generateGstin('27');    // ... for Maharashtra
generatePan('C');       // ... entity Company (unknown char falls back to 'P')
generateMobile();       // e.g. '6308893624'
generateVehicle();      // e.g. 'TN02D6788'
generateVehicleBharat(); // e.g. '22BH1234AA'
```

```python
from indycheck import generate_pan, generate_aadhaar, generate_gstin

generate_pan()      # e.g. 'HMSTC9464C'
generate_aadhaar()  # e.g. '262200939149'
generate_gstin("27")  # e.g. '27...' — for Maharashtra
```

```rust
use indycheck::generate_pan;

let pan = generate_pan('P'); // e.g. "HMSTC9464C"
```

## What the generators produce

| Function | Example output | Guarantee |
| --- | --- | --- |
| `generatePan(entity?)` | `HMSTC9464C` | Valid format (entity reported) |
| `generateAadhaar()` | `262200939149` | Passes the Verhoeff checksum |
| `generateGstin(stateCode?)` | `13NFAPJ0888B1ZM` | Valid state, valid PAN part, correct Mod-36 Luhn check char |
| `generateMobile()` | `6308893624` | 10 digits, starts 6–9 |
| `generateVehicle()` | `TN02D6788` | Valid standard shape (state + district + series + number) |
| `generateVehicleBharat()` | `22BH1234AA` | Valid Bharat shape (year 21–26, `BH`, number, suffix without `I`/`O`) |

There are no generators for IFSC, UPI, PIN code, TAN, CIN, LLPIN or Voter ID. Every generated value passes its own validator — this is covered by tests in the package. Generators are intentionally unseeded: each call may return a different value.

## Patterns for tests

```js
import { describe, it, expect } from 'vitest';
import { generatePan, validatePan } from 'indycheck';

describe('signup form', () => {
  it('accepts a generated PAN', () => {
    const pan = generatePan();
    expect(validatePan(pan).valid).toBe(true);
  });

  it('rejects a PAN with a broken format', () => {
    // Flip the last character of a valid PAN to a digit — the shape
    // no longer matches 5 letters + 4 digits + 1 letter. (PAN has no
    // checksum, and the 4th character is reported, not enforced — so
    // corrupting the holder-type character would still validate.)
    const pan = generatePan();
    const bad = pan.slice(0, 9) + '5';
    expect(validatePan(bad).code).toBe('INVALID_FORMAT');
  });
});
```

```python
from indycheck import generate_aadhaar, generate_gstin, validate_aadhaar, validate_gstin

def test_generated_aadhaar_is_valid():
    assert validate_aadhaar(generate_aadhaar())["valid"]

def test_generated_gstin_round_trips():
    gstin = generate_gstin()
    assert validate_gstin(gstin)["parsed"]["state"]
```

## Seeding a demo database

```js
import { generatePan, generateMobile } from 'indycheck';

const demoCustomers = Array.from({ length: 20 }, (_, i) => ({
  id: i + 1,
  name: `Demo Customer ${i + 1}`,
  pan: generatePan(),
  mobile: generateMobile(),
  // Label the row so nobody mistakes it for real data:
  is_test_data: true,
}));
```

## TEST DATA ONLY — read this

<Aside type="caution" title="Generated values are not real IDs">
  - **Never present a generated value as a real person's ID** — not in a demo, not in a screenshot, not in a support ticket. A generated PAN looks exactly like a real one; that is the point, and the risk.
  - **Never use generated values to impersonate anyone** or to test a real verification provider — providers will (correctly) reject them, and repeated attempts can look like fraud.
  - **Mark test data clearly** — in the UI (`TEST DATA ONLY` badge, as the [playground](/playground/) does), in the database (`is_test_data: true`), and in screenshots.
  - A generated value **could in principle collide** with a real issued number. Treat every generated value as untrusted dummy data and delete it when the test is done.
</Aside>
