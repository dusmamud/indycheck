All three bindings — JavaScript/TypeScript, Python and Rust — expose the same validators and the same result shape. The rules live in one Rust core, so results never differ between languages. (The other language packages — Go, PHP, Dart, Kotlin, Swift and C — wrap the same core; see their own pages.)

## Install

```bash
npm install indycheck
pip install indycheck
cargo add indycheck
```

## Functions

There is no generic `validate(type, value)` / `generate(type)` / `mask(type, value)` / `format(type, value)` dispatcher. Each ID type has its own named validator, and masking, formatting and test-data generation are per-type functions too (see [Masking & formatting](/masking-formatting/) and [Test-data generators](/generators/)).

| Validator | JS/TS | Python | Rust |
| --- | --- | --- | --- |
| Mobile | `validateMobile(value)` | `validate_mobile(value)` | `validate_mobile(value)` |
| PAN | `validatePan(value)` | `validate_pan(value)` | `validate_pan(value)` |
| Aadhaar | `validateAadhaar(value)` | `validate_aadhaar(value)` | `validate_aadhaar(value)` |
| GSTIN | `validateGstin(value)` | `validate_gstin(value)` | `validate_gstin(value)` |
| IFSC | `validateIfsc(value)` | `validate_ifsc(value)` | `validate_ifsc(value)` |
| UPI ID | `validateUpi(value)` | `validate_upi(value)` | `validate_upi(value)` |
| PIN code | `validatePincode(value)` | `validate_pincode(value)` | `validate_pincode(value)` |
| TAN | `validateTan(value)` | `validate_tan(value)` | `validate_tan(value)` |
| CIN | `validateCin(value)` | `validate_cin(value)` | `validate_cin(value)` |
| LLPIN | `validateLlpin(value)` | `validate_llpin(value)` | `validate_llpin(value)` |
| Voter ID | `validateEpic(value)` | `validate_epic(value)` | `validate_epic(value)` |
| Vehicle | `validateVehicle(value)` | `validate_vehicle(value)` | `validate_vehicle(value)` |

Aliases: `validateVoterId` / `validate_voter_id` and `validateVehicleRegistration` / `validate_vehicle_registration` are the same validators as `validateEpic` and `validateVehicle`.

### With options

Only mobile, PAN, Aadhaar and GSTIN take options — as `validate*WithOptions(value, options)` in JS, `validate_*_with_options(value, options)` in Python, and `validate_*_with_options(value, options)` in Rust. The other validators take no options argument. See [Options](/options/) (`strict`, `allow_spaces_hyphens`, `normalise_plus91`, `uppercase`).

### Detect and batch

| Function | JS/TS | Python | Rust |
| --- | --- | --- | --- |
| Detect the type | `detectType(value)` → type string; `detect(value)` → full result | `detect_type(value)` → type string; `detect(value)` → full result | `detect(value)` → type string |
| Batch | `validateMany(inputs)` | `validate_many(inputs)` | `validate_many(inputs)` |

`detectType` / `detect_type` returns one of `'pan'`, `'aadhaar'`, `'gstin'`, `'ifsc'`, `'upi'`, `'mobile'`, `'pincode'`, `'tan'`, `'cin'`, `'llpin'`, `'voter'`, `'vehicle'` or `'unknown'`. In JS and Python, `detect(value)` runs the matching validator as well and returns its full result in `parsed.result`; in Rust, `detect(value)` returns just the type string. In JS and Python, `validateMany` accepts an array of strings (or `{ type, value }` objects) and returns one result whose `parsed` holds the per-item results; in Rust, `validate_many` returns a `Vec<ValidationResult>`, one per input, in order. An undetectable input gets code `UNKNOWN_TYPE`.

## Result shape

Every validator returns the same object (shown here as JSON; Python returns a dict, Rust a struct, with the same fields):

```json
{
  "valid": true,
  "code": "VALID",
  "reason_en": "PAN format is valid. PAN has no public checksum, so this only checks the format",
  "reason_hi": "PAN ka format sahi hai. PAN ka koi public checksum nahi hai, isliye sirf format check hua hai",
  "parsed": {
    "entity": "Individual",
    "entity_code": "P"
  }
}
```

| Field | Type | Always present? | Meaning |
| --- | --- | --- | --- |
| `valid` | boolean | Yes | `true` only when the value is fully valid |
| `code` | string | Yes | Machine-readable result — see error codes below |
| `reason_en` | string | Yes | Human-readable reason in English |
| `reason_hi` | string | Yes | The same reason in Hindi (Roman script) |
| `parsed` | object or `null` | Yes in JS/Python (`null` on failure); omitted in Rust JSON on failure | Structured fields extracted from the value |

There is no `ok`, `type`, `value` or top-level `normalized` field on a result. The cleaned-up value, where one exists, lives inside `parsed` — for example `parsed.normalized` on a successful mobile result.

### `parsed` by validator

| Validator | `parsed` fields |
| --- | --- |
| Mobile | `normalized` |
| PAN | `entity`, `entity_code` |
| Aadhaar | `masked` (e.g. `XXXX XXXX 0124`) |
| GSTIN | `state`, `state_code`, `pan` |
| IFSC | `bank_code`, `branch_code` |
| UPI ID | `handle` |
| PIN code | `pincode` |
| TAN | `tan` |
| CIN | `cin`, `listing`, `industry_code`, `state_code`, `year`, `company_type`, `registration_number` |
| LLPIN | `llpin` |
| Voter ID (EPIC) | `epic` |
| Vehicle | `registration`, `series_type` (`"state"` or `"bharat"`), `state_code`, `district`, `series`, `number`; Bharat adds `year`, `suffix` |

The full machine-readable code table — including `UNKNOWN_TYPE` (from `detect()` / `validate_many()` when no type fits) — lives on the [Error codes](/error-codes/) page.

## Error codes

`code` is stable across releases — branch on it, not on the reason strings.

| Code | Meaning | Validators |
| --- | --- | --- |
| `VALID` | Fully valid | all |
| `EMPTY` | Input was empty / only whitespace | all |
| `INVALID_TYPE` | Input was not a string (JS/Python only) | all |
| `INVALID_LENGTH` | Wrong length | all except mobile, UPI ID |
| `INVALID_FORMAT` | Characters or pattern don't match (wrong separators, illegal characters, wrong fixed character) | all |
| `INVALID_CHECKSUM` | Checksum digit fails (Verhoeff for Aadhaar, Mod-36 Luhn for GSTIN) | Aadhaar, GSTIN |
| `INVALID_FIRST_DIGIT` | First digit not allowed (0/1 for Aadhaar, 0 for PIN, not 6–9 for mobile) | Aadhaar, mobile, PIN |
| `INVALID_STATE_CODE` | First two digits are not an Indian state/UT code (01–38) | GSTIN |
| `INVALID_ENTITY` | Reserved — an unlisted PAN 4th character is reported as entity `"Unknown"` instead, and the PAN is still valid | never emitted as of v0.2.5 |
| `INVALID_HANDLE` | UPI handle is missing or not a known handle | UPI ID |
| `UNKNOWN_TYPE` | The value matches no known ID format | `detect()` / `validate_many()` only |
| `SOME_INVALID` | Some inputs in a batch were invalid (JS/Python `validateMany` wrapper only; Rust returns a plain list) | `validateMany` only |

### Precedence

When several things are wrong, indycheck reports the first check that fails. The order depends on the validator — for example Aadhaar is `EMPTY` → `INVALID_LENGTH` → `INVALID_FORMAT` → `INVALID_FIRST_DIGIT` → `INVALID_CHECKSUM`, and GSTIN is `EMPTY` → `INVALID_LENGTH` → `INVALID_FORMAT` → `INVALID_STATE_CODE` → `INVALID_FORMAT` (PAN part / `Z` / entity character) → `INVALID_CHECKSUM`. See the [Error codes](/error-codes/) page for the full per-validator orders. So `234567890123` reports `INVALID_CHECKSUM`, not a format error — the shape is right, the digit is wrong.

## Usage patterns

### Branch on `code`, show `reason_hi` / `reason_en`

```js
import { validatePan } from 'indycheck';

const r = validatePan(userInput);
if (!r.valid) {
  // Show Hindi to Hindi-speaking users, English otherwise.
  showError(lang === 'hi' ? r.reason_hi : r.reason_en);
}
```

### Batch validation

```js
import { validateMany } from 'indycheck';

const r = validateMany(['AAAPL1234C', '5123456789', '9876543210']);
console.log(r.parsed.validCount, 'of', r.parsed.total, 'valid'); // 2 of 3 valid
const bad = r.parsed.results.filter((x) => !x.valid);
console.log(bad); // [{ input: '5123456789', type: 'mobile', code: 'INVALID_FIRST_DIGIT', ... }]
```

```python
from indycheck import validate_many

r = validate_many(["AAAPL1234C", "5123456789", "9876543210"])
bad = [(x["input"], x["code"]) for x in r["parsed"]["results"] if not x["valid"]]
print(bad)  # [('5123456789', 'INVALID_FIRST_DIGIT')]
```

### Never log Aadhaar

```js
import { validateAadhaar } from 'indycheck';

const r = validateAadhaar(aadhaarInput);
if (r.valid) {
  db.save({ aadhaar_masked: r.parsed.masked }); // XXXX XXXX 0124 — never the full number
}
```

<Aside type="caution" title="Honest limits">
  indycheck validates format and checksum only. A result of `valid: true` never means "this ID exists" or "this ID belongs to this person". There is no network call, no UIDAI/NSDL/GSTN/MCA/ECI lookup, and no database of real IDs anywhere in the package. TAN, CIN, LLPIN, Voter ID and vehicle numbers have no public checksum at all — for those, indycheck checks the format only.
</Aside>
