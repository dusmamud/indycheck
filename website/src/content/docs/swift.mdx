The Swift bindings are generated [UniFFI](https://mozilla.github.io/uniffi-rs/) bindings over the Rust core in `crates/indycheck-uniffi`. **No validation logic lives in Swift** — every function calls the matching core validator and returns a `ValidationResult` struct whose `parsed` field is the core result's `parsed` object serialised as a JSON string (or `nil` when there is none). Keeping `parsed` as JSON keeps the interface identical in Swift and Kotlin.

<Aside type="note" title="Status — Swift Package (0.2.4)">
  The Swift package is published as `IndyCheck` — add it in Xcode or SwiftPM (see below). It ships the UniFFI Swift bindings as a binary target backed by the prebuilt `IndyCheckFFI.xcframework` (iOS arm64 + simulator, macOS universal) from the 0.2.4 GitHub release. The bindings are **compile-verified in CI with a `validatePan` smoke test only** — there is no full Swift test suite yet.
</Aside>

## Install

**Xcode:** File → Add Package Dependencies → `https://github.com/dusmamud/indycheck-swift` → version **0.2.4**.

**SwiftPM** (`Package.swift`):

```swift
.package(url: "https://github.com/dusmamud/indycheck-swift", from: "0.2.4")
```

Then `import IndyCheck`. The package ships the UniFFI bindings plus the prebuilt XCFramework — no Rust build step, no manual file copying. Requires iOS 13+ / macOS 11+.

Building from source instead: the generated bindings live in `crates/indycheck-uniffi/bindings/swift/` (`indycheck_uniffi.swift`, `indycheck_uniffiFFI.h`, `indycheck_uniffiFFI.modulemap`). Build the Rust core as a library for your target (via `cargo build -p indycheck-uniffi`) and link it. CI compiles the bindings with `swiftc` and passes the modulemap explicitly (`-Xcc -fmodule-map-file=...`); if you wire the files into an Xcode project, make sure the modulemap is on the compiler's include path the same way. To regenerate the bindings after a core change, see the README in `crates/indycheck-uniffi/`; do not edit the generated files by hand.

## Example

```swift
let pan = validatePan(input: "ABCDE1234F")
print(pan.valid, pan.code) // true VALID

if !pan.valid {
    print(pan.reasonEn, "/", pan.reasonHi)
}

// Bharat (BH) series vehicle number
let vehicle = validateVehicle(input: "22BH1234AA")
print(vehicle.valid, vehicle.parsed ?? "")
// parsed is a JSON string, e.g. {"series_type":"bharat","year":22,...}
// — decode it with JSONDecoder / JSONSerialization

// Detect the type first, then validate a batch in one call
print(detect(input: "9876543210")) // mobile
let batch = validateMany(inputs: ["ABCDE1234F", "9876543210", "nope"])
print(batch.map { $0.valid }) // [true, true, false]
```

## API

Top-level functions, verified in the generated `indycheck_uniffi.swift`:

| Function | Returns |
|---|---|
| `validatePan(input:)` | `ValidationResult` |
| `validateAadhaar(input:)` | `ValidationResult` |
| `validateGstin(input:)` | `ValidationResult` |
| `validateIfsc(input:)` | `ValidationResult` |
| `validateUpi(input:)` | `ValidationResult` |
| `validateMobile(input:)` | `ValidationResult` |
| `validatePincode(input:)` | `ValidationResult` |
| `validateVehicle(input:)` | `ValidationResult` (incl. Bharat `22BH1234AA`) |
| `validateTan(input:)` | `ValidationResult` |
| `validateCin(input:)` | `ValidationResult` |
| `validateLlpin(input:)` | `ValidationResult` |
| `validateVoterId(input:)` | `ValidationResult` |
| `detect(input:)` | `String` (`"pan"`, `"aadhaar"`, … or `"unknown"`) |
| `validateMany(inputs:)` | `[ValidationResult]` |

```swift
public struct ValidationResult {
    public var valid: Bool
    public var code: String       // "VALID" on success, otherwise a stable error code
    public var reasonEn: String
    public var reasonHi: String
    public var parsed: String?    // JSON string, or nil when there is nothing to parse
}
```

`valid` is true only on success; `code` is `"VALID"` then, otherwise a stable error code such as `"INVALID_CHECKSUM"`.

## What is not here yet

- **No `validateEpic` alias.** The UniFFI interface exports `validateVoterId` only — use that for Voter ID / EPIC. (The Rust core, JS/Python wrappers, Dart, PHP, Go and C all have a `validateEpic` alias; Kotlin and Swift do not.)
- **No test-data generators and no `version()`.** The UniFFI interface has no `generate_*` functions and no version function — only the 12 validators, `detect` and `validateMany` listed above. If you need mock test data, generate it with the Rust core, the CLI, or another wrapper.
- **No options variants.** There are no `validate*WithOptions` functions yet — validation always uses the core defaults.
- **No full test suite.** CI only compiles the bindings and runs a `validatePan` smoke test. The core itself is fully tested in Rust; the Swift surface is not.
